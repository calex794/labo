# EXP-015 — сравнительный опыт: искать получателя или ближайший интернет-шлюз

## Постановка
Продолжение EXP-012. Основное отличие: в EXP-012 установлено gateways=(), mailbox_authorized=False — тем самым сравнение PRoPHET и Parallel вообще не испытывало маршрут через интернет-шлюз. Новая модель сравнивает 4 стратегии при **одной K4**:
1. `recipient_prophet4`: история встреч ведёт к самому адресату.
2. `gateway_direct4`: письмо передаётся только при непосредственной встрече с согласным шлюзом (или адресу).
3. `gateway_history_prophet4`: по **исторической** карте выбирается ближайший известный шлюз; PRoPHET4 переносит сообщение к нему. Смоделированное «дошло до получателя» здесь означает **только поступление к шлюзу**, не W4.
4. `hybrid_parallel4`: существующий Parallel4 с получателем, прогнозом и независимой веткой шлюза в общей K4.

## Метод
- Реальные наблюдения — два независимых обезличенных журнала SocioPatterns SFHH 2009 и InVS 2015, по 20 секунд. Скачивание только по закреплённым исходным Git blob SHA из EXP-012. Отдельные CSV с контактами не сохранять в артефактах.
- Обучение — первые 25% наблюдённых временных отметок. Адресаты выбираются только из этого периода; раннее/позднее испытание — 45% и 70% хронологии, одинаковые письма для всех маршрутов.
- Согласие и доля шлюзов **синтетические**: 2% и 10% узлов, встреченных при обучении. Выбор детерминирован, после обучения не использует будущие встречи. **Не** реальное согласие участников, не частота смартфонов с интернетом.
- Время получения адресатом из ящика **условное**: каждый 1 или 2 часа от момента появления письма, и только после фактического депонирования. Просто `mailbox_stored` не засчитывать доставкой. Интернет-шлюз считается постоянно доступным по допущению.
- Одна K4 для каждого письма; BLE сообщение 256+64 байт, хорошая скорость 64 кбит/с, контактная запись 20 секунд — **модельные предположения**, не реальные измерения BLE.
- 2 источника × 2 периода × 2 seed × 2 доли шлюзов × 2 режима получения × 4 стратегии = 128 прогонов сценариев/политик; две категории адресатов → 256 строк результата; попарные различия для 3 стратегий против прямого PRoPHET — 192 строки.
- Сравнение: принятые адресатом сообщения, отдельно по встречам и через ящик; помещения в ящик; общий эфир в байтах, предполагаемый интернет-трафик, бюджет K, максимум радиовремени, попарные победы по **тем же** письмам. Полные байты запуска повторяются по категориям: **не суммировать строки категорий**.

## Границы подтверждений
- Реальные: только факты близких встреч анонимных участников.
- Смоделированные: передача письма, доступность шлюзов, согласие, интернет, расписание опроса ящика, энергия, квитанция. Это не проверка живого Bluetooth, приватности W3 v3, подписи W4 или повседневной доступности шлюза.
- Состояния: `gateway_stored` НЕ `recipient_accepted`; `recipient_accepted` — модельное событие, а не подписанный WOW W4. Даже успешный CI доказывает лишь результат этой модели.
- Модель маршрута к шлюзу предполагает заранее известный список добровольных шлюзов. У реальной Акулы эта информация должна поступать через разрешённые приглашения/объявления, без выдачи постоянного ID конечного адресата.
- Шлюз на пути не может менять исходный зашифрованный W3. Дополнительная внешняя обёртка допустима; подписи, доверие, отзыв и граница File Gate остаются отдельными.

## Воспроизведение
```bash
python3 -m unittest discover -s scripts -p 'test_exp015_gateway_comparison.py' -v
python3 scripts/exp015_gateway_comparison.py --download \
  --cache results/exp012-source-cache --output results/exp015 \
  --seeds 21021 21022 --gateway-percent 2 10 \
  --pickup-hours 1 2 --letters-per-kind 12 --ttl-hours 4
```

## Следующие контрпримеры и улучшения
1. Временно выключить шлюзы посреди интервала: периодические провалы интернета, смена устройства, отсутствие разрешения ящика.
2. Задержанная доставка и обратная квитанция W4 как **два независимых пути**: доставка ≠ возврат подписанного подтверждения.
3. Подписанные разрешения на хранение и аварии двух независимых SQLite, не переносить модельную глобальную K4 в production.
4. Проверить чувствительность к доле шлюзов, выбору людей, TTL и частоте проверки почты; избегать подгонки параметров под известные результаты.
5. Отделить произвольную шлюзовую метку от права доступа: маршрутный токен виден пересыльщику и не может в одиночку быть полномочием.
6. Эксперимент на реальных двух ПК и мобильном Bluetooth до утверждений о сети Akula.
