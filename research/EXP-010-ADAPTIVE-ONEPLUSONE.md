# EXP-010 — адаптивный 1+(1): прогноз встреч + ограниченная разведка

**22 октября 2026. Статус: исходный код подготовлен для проверки в GitHub Actions.**

[LABO-ROUTE-001 в Notion](https://app.notion.com/p/40032a84beec81768202c3faf8054e83) · [задание №8](https://github.com/calex794/labo/issues/8) · [исходный EXP-009b](EXP-009-ONEPLUSONE.md)

## Задача

У первоначального `oneplusone2/4` активная копия выбирала первого согласного добровольца, часто уходила в тупик. У `oneplusone_predict2/4` активный носитель использует историю прошлых контактов, но **не передаёт письмо при неизвестном или устаревшем маршруте**. EXP-010 проверяет сочетание этих стратегий **при одном глобальном бюджете копий** и сохранении резервов только для прямой встречи с точным получателем.

## Новый алгоритм

`oneplusone_adaptive2`: не более **1 подвижной + 1 резервной** копии.

`oneplusone_adaptive4`: не более **1 подвижной + 3 резервных** копий.

Для каждого уже наблюдаемого контакта A→B:
1. Если B — **точный получатель**, передать ему письмо сразу при наличии времени на передачу; зарегистрировать только одно логическое принятие (симуляция; настоящей подписи W4 нет).
2. Если текущая копия **резервная**, никому, кроме получателя, её не передавать.
3. У активной копии получить `score(A,D)`, `score(B,D)`, возраст последнего обновления оценки. Если `score(B,D) > score(A,D)+0,08`, `score(B,D)>=0,10` и возраст оценки B не более **6 модельных шагов**, то передавать по прогнозу PRoPHET.
4. Если свежий собственный прогноз A достаточно хорош (возраст не более 6 шагов, оценка не меньше 0,10), **не бросать его** ради слепого поиска.
5. Если надёжного свежего прогноза нет — передавать только **ранее не использованному** добровольному переносчику со специальной ролью путешествующего между корпусами (идентификатор `id % 2000 == 1`) либо к участнику **ещё не посещённого** корпуса. Это только эвристика генератора LABO, а не реальный признак географического положения человека.
6. Число успешных разведочных передач за весь срок одного письма **не более `2 × K`**. Нет возможности — продолжаем хранить письмо до следующего контакта.
7. После успешной передачи старый носитель сохраняет **резерв**, пока у сообщения есть свободная квота; после заполнения K подвижная копия **перемещается** без рождения новой копии.
8. Тот же TTL, ограничения добровольности, общие эфирные квоты и невозможность двух последовательных пересылок в один шаг, что и в EXP-008/009.

**Возраст оценки** — время от последнего пересчёта, который мог быть косвенным, а не строго от личной встречи с получателем. Поэтому «свежая» оценка **не значит** «человек видел получателя». Числа 0,08, 0,10, 6 и `2×K` — инженерные гипотезы для сравнения, не замеренные свойства Bluetooth или социальной сети.

## Подтверждающие / опровергающие контролируемые маршруты

| Модельный маршрут | Ожидаемое различие |
|---|---|
| **Ранее неизвестная цепочка курьеров**: 0→1→2000→2001→4000 | Адаптивный 1+(1) может пройти, строгий прогноз без истории — нет |
| **Изменение привычек**: в начале узел 4 видел адресата 5; через 8 шагов приходит новый курьер 2001, который затем встречает 5 | Адаптивный игнорирует устаревшую подсказку и может пойти с новым курьером |
| **Свежая история**: 2 только что встречал 5; отправитель встречает 2 | Выбираем 2 по прогнозу, даже если он не помечен курьером |
| **Резерв встречает адресата** после ухода бегущей копии | Резерв вручает конверт лично 1 раз, посторонним не пересылает |
| **Неверный первый курьер** идёт в тупик, обычный второй сосед встретит адресата | Адаптивный может проиграть Spray и другим способам |
| **Нет наблюдаемого перспективного контакта** | Алгоритм не придумывает маршрут и не использует знание будущего |

Контакты подобраны специально, чтобы **показать и выигрыш, и проигрыш**. Они не являются выборкой реальных траекторий людей. Никаких выводов о средней доле успеха на настоящих смартфонах делать нельзя.

## Проверка при одинаковом ресурсе

```bash
python3 -m unittest discover -s scripts -p 'test_exp010_adaptive_routing.py' -v
python3 scripts/exp010_adaptive_routing.py --output results/exp010
```

Одна матрица: 1/10/100 корпусов, по 2 000 виртуальных устройств, 3 одинаковых зерна, 80 условных шагов, TTL40, 256-байтные письма при условной скорости 64 кбит/с, переносчики между корпусами разрешены, идеальное сканирование, без IP-шлюза; 10 стратегий × 3 размера × 3 зерна = **90 симуляций**, **150 строк по двум категориям адресатов** (для одного корпуса — одна категория), **90 парных сравнений одинакового K**, **60 строк контрольных трасс**. Файлы: `routing-matrix.csv/json`, `equal-copy-comparisons.csv`, `changing-routines.csv/json`, `report.md`.

K=2 сравнивается **только с K=2**, K=4 — с K=4. Случайные адресаты и специально выбранные пары соседних хабов считаются **отдельно**. `wire_bytes` повторяется для каждой категории в одной симуляции; значения **нельзя складывать** по двум категориям.

Проверки: изменение маршрутов, отсутствие знания будущего, общий предел K, отсутствие повторного размножения, запрет передачи резервов неадресату, добровольность, конкуренция за эфир, TTL, неизменность старых политик, один логический приём письма. Отдельная профильная проверка добавлена **в существующее единственное задание** EXP-009, без нового веера тяжёлых Rust-тестов.

## Чего в LABO пока нет

- **Настоящей частной проверки адресата**: публичный числовой ID не удовлетворяет требованиям безопасности Akula.
- **Защищённого журнала полномочий K после отключения двух телефонов**: квоты гарантируются только в честной однопроцессной модели.
- Реальных записей Bluetooth-обнаружения, скорости, батареи, событий пребывания людей и фрагментированной передачи.
- **Криптографически подписанной квитанции W4** и интеграции с производственным приложением Akula.

**Следующее научное задание:** воспроизведение на временных журналах реальных контактов (SocioPatterns/Briar) и изменение распределения связей по эпохам, без выдуманного знания будущих встреч. Продолжать только если критерий `доставки на байт` лучше хотя бы в части независимых реалистичных режимов.
