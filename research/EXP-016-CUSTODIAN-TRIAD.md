# LABO EXP-016 — один личный и два общих почтовых кастодиана

**Цель:** проверить реальным исполнением отдельный фрагмент [WOW-CUSTODIAN-02](https://app.notion.com/p/40132a84beec8139a590c29e7a4eaa8c): письмо можно сохранить на личном P, отключить отправителя, перенести право хранения на общий X/Y, а позднее найти письмо через закрытое приглашение получателя.

**Граница доказательства:** отдельный опыт LABO. Реальные W3/HPKE, Ed25519/COSE/W4, BLE, QUIC и Akula здесь НЕ запускаются; общий [WOW issue #67](https://github.com/calex794/wow/issues/67) остаётся нерешённым.

## Участники

| Участник | Роль | Состояние |
|---|---|---|
| A | Отправитель, создаёт синтетический закрытый конверт | Выключается в модели после первичной записи |
| P | PERSONAL — личный кастодиан | Собственный SQLite P.sqlite |
| X | PUBLIC — добровольный кастодиан | Собственный SQLite X.sqlite, временно недоступен |
| Y | PUBLIC — второй независимый оператор | Собственный SQLite Y.sqlite |
| B | Получатель | Знает только X/Y и закрытые метки ящиков |

Каждая операция P/X/Y запускается в своём отдельном процессе Python, а каждый узел работает со своим файлом SQLite с WAL+FULL. Повторное открытие после завершения процесса проверяет долговременную запись на уровне SQLite. Все процессы исполняются на одном Linux-исполнителе GitHub: это не три физических сервера. Передача выполняется через локальный JSON stdin/stdout управляющего процесса, а не через настоящую сеть.

## Порядок опытов

1. A помещает три набора случайных байтов (три независимых письма) на P. Каждый имеет собственный единичный слот C; условная схема K3 — исходник A, один подвижный R, одно право C. Роль R через BLE здесь не исполняется.
2. A и R более не участвуют. X условно недоступен. P передаёт первый C-слот Y, Y устойчиво сохраняет точные байты и подписывает *тестовую HMAC-квитанцию*; P перестаёт быть активным хранителем. B находит первое письмо по закрытой метке Y.
3. X возвращается. P передаёт второй слот X, но его подтверждение теряется. P НЕ вправе передать этот же слот Y. Повтор того же предложения X возвращает ранее выданную квитанцию; P завершает перенос. B получает второе письмо.
4. Третье письмо остаётся у P, неизвестного B. При запросах B только к X/Y письмо не находится — контроль против ложной доставляемости при слепом выборе общих кастодианов.
5. Чужой секрет чтения, подделка хеша, неверная цель, повтор конфликтующего предложения, переполнение почтового ящика и истечение разрешения отклоняются.

## Ограничения и угрозы

- Узлы используют ТОЛЬКО тестовый HMAC с общими ключами, известными испытательному процессу; это НЕ реальная аутентификация распределённых недоверенных пользователей. В production потребуются публичные ключи и подписи WOW.
- Получение B означает возврат тех же случайных байтов с правильным хешем, а НЕ подписанную конечную W4; до отдельной W4 статус «доставлено» выставлять нельзя.
- Отключение sender/runner и X моделируется отсутствием вызовов, не выключением физических устройств.
- Общий K3 ограничивает *разрешённые логические права честных узлов*, не байтовые копии в обход протокола.
- Потеря ACK создает неопределённость, в которой слот не выдаётся другому узлу. Нет гарантии глобальной квоты против злонамеренного отката БД.
- Публичные объявления P/X/Y содержат только адрес службы, режим и лимит, без тегов ящика или личности получателя; реальные сетевые метаданные/анонимность здесь не проверяются.
- Пользовательский Vault и File Gate не подключаются. Никакие реальные сообщения пользователя не копируются.

## Воспроизведение

Только Python 3 и стандартная библиотека. Проверки в корне LABO:

1. python3 -m unittest discover -s scripts -p 'test_exp016_custodian_network.py' -v
2. python3 scripts/exp016_custodian_network.py run --output results/exp016

Выходные файлы: results/exp016/custodian-triad.json и report.md, без самих БД/секретов/синтетических писем. Узкий GitHub Actions запускается только при изменении четырёх файлов EXP-016.

**Критерии:** 12 проверок Python, полный сценарий трёх SQLite, точные конечные состояния P=FORWARDED/FORWARDED/ACTIVE; X=ABSENT/ACTIVE/ABSENT; Y=ACTIVE/ABSENT/ABSENT; контролируемая недоставка третьего письма; K3 без двойной выдачи после lost ACK; отрицательные права и подделки.

## Следующая физическая проверка

Два самостоятельных сервера и клиент B на разных устройствах, реальный Roha/noq, W3 v3 с проверкой идентичности/HPKE, конечная подписанная W4, отказ после записи, перезапуск устройства, отзыв приглашения, лимиты чужих писем, отказ общего C и восстановление маршрутов. После этого можно говорить о внедрении в WOW/Akula, а не после одного зелёного CI.
