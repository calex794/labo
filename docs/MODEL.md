# Математическая модель LABO v0

**Предмет:** сравнивать возможности связи и отложенной доставки при движении, отказах и различной геометрии. Это вычислительный эксперимент, а **не измерение Bluetooth, LTE или Wi-Fi**, не криптографический протокол и не готовый мессенджер Акулы.

## Пространство

- **building:** пять этажей, на каждом 70 комнат (35 вдоль каждой стороны коридора); продольные позиции через условные 10 м. Пять сквозных лестниц по координатам x=58, 116, 174, 232, 290. Переходы происходят только из комнаты в коридор, вдоль коридора и через лестницу; смена этажа только внутри лестницы.
- **plaza:** открытая условная квадратная площадь 500 × 500 м, движение шагами по двум осям без телепортации.
- Любые «метры» и вероятности стен в v0 **гипотетические**; до использования настоящих инженерных чисел требуется калибровка по ITU-R P.1238 и физическим замерам. Лестница не даёт автоматической радиосвязности между всеми этажами.

## Состояния

Для устройства i: позиция p_i(t), этаж, тип радиомодулей c_i, флаг добровольного транзита o_i, подвижность m_i, доступность a_i(t). Для сообщения m: отправитель, адресат, текущее устройство-носитель, t0, срок жизни, отметка виртуальной доставки, число переходов.

- **wifi:** все имеют общий доступ к идеализированной локальной Wi-Fi сети, без моделирования точек доступа и помех. Это верхняя контрольная оценка; локальный Wi-Fi не тождествен доступу в интернет.
- **hybrid:** пример долей 30% BLE, 30% Wi-Fi+BLE, 40% Wi-Fi; это **выбранные гипотезы**, не перепись телефонов.
- **ble:** каждый имеет только BLE.
- **exclusive:** примерно равные доли только Wi-Fi, только сотовой IP-связи и только BLE. **Нет** скрытого BLE↔IP мостика; `--ip-interconnect` допускает исключительно Wi-Fi↔сотовый IP (при допущении общей IP-маршрутизации), Bluetooth не включается в этот мост.

Вопрос «можно ли установить контакт» вычисляется на основании совместимых активных интерфейсов, наличия IP-пути или пространственной BLE-близости и возможности фоновой активности (пока последнее свернуто в общий флаг «онлайн»). Межэтажный BLE переход разрешён лишь соседним этажам, если оба находятся в одной и той же лестнице.

## Время и перемещение

`static`: все неподвижны; `quarter`: в начале выбирается случайная четверть подвижных; `all`: могут двигаться все. На каждом виртуальном шаге подвижные устройства с вероятностью 30% обновляют положение по разрешённым переходам. Это простая контрольная модель, ещё не Working Day Movement Model, реальные очереди лестниц или планы эвакуации.

`never`: канал не отключается; `once`: условно у 1/5 устройств связь отсутствует в средней трети эксперимента; `periodic`: периодические детерминированные окна недоступности. Сейчас `online` — доступность всего устройства, а не отдельного радио/фонового процесса. Последние состояния должны появиться в последующей серии.

## Схема работы

Используется 1 носитель для каждого сообщения (store–carry–forward, **без создания копий**), ограничение 16 передач, волонтёрское согласие `relay_percent`, одинаковые оригинальные сообщения и ограниченное число `contact-probes` на шаг. Пространственный индекс: `HashMap<(floor,cell_x,cell_y), Vec<device_id>>`; нет матрицы N×N.

Оценка сложности: около O(T·(N + M·K)) операций, память порядка O(N + M + численность пространственного индекса), где N — количество устройств, M — активные сообщения, K ≤ 64 — число предложений контакта, T — виртуальных шагов. Это **верхний порядок для реализованной модели**, не гарантия времени исполнения на конкретной машине.

**Важно:** в v0 выбираются случайные согласившиеся соседи; это не полный алгоритм поиска оптимального маршрута, не настоящий DTN Spray-and-Wait, не шифрование и не подписанные конечные квитанции. Доставка в отчёте означает лишь достижимый во временной модели **контакт адресата**, а не проверку устройства, сохранение в SQLite или отображение в чате Акулы. Нельзя выдавать числа доставки из LABO за пользовательский результат.

## Отчёт

JSON поле `claim` всегда `synthetic-not-measured`. Указываются создаваемые/доставленные/просроченные/ожидающие сообщения, доля доставленных, промежуточные пересылки, ограниченные попытки контакта, блокировки из-за офлайна и p50/p95 **в виртуальных шагах**. При сравнении вариантов сначала фиксировать seed и конфигурацию, затем повторять несколько независимых seed: один прогон не доказывает статистическую устойчивость.

Матрица `4 режима × 3 подвижности × 3 отключения = 36` запускается `--matrix`. Для настоящих результатов требуется калибровка BLE/Wi-Fi/LTE, согласованные распределения движения, нагрузка на батарею и фоновые ограничения ОС.

## Проверки безопасности и масштабирования

1. Один seed + параметры = одинаковый отчёт.
2. Только Wi-Fi и все в одной LAN → все созданные сообщения доставляются в пределах контрольного окна (если нет отказа).
3. В режиме строго одного радиоинтерфейса BLE↔IP **не появляется** даже при движении.
4. BLE между этажами — только через одну лестницу соседних этажей.
5. Отключённому адресату сообщение доставляется после восстановления, если не истекло TTL.
6. Для 200 000 устройств пространственный индекс строится без N² памяти.
7. `delivered + pending + expired = created`; недоставленные не исчезают из отчёта.

Референсы: [LesHa virtual-time](https://app.notion.com/p/3ec32a84beec81fca9dece197148b7c4), [AK-MSG-SIM-2000](https://app.notion.com/p/40032a84beec8113a9e0ddd204081f50), [Akula CORE](https://app.notion.com/p/40032a84beec81919ec8df2e31056543).

В дальнейшем результаты можно передавать в Акулу через **версионированный отчёт и сценарии проверок**, а не добавляя в её ядро математические модели и генераторы.
